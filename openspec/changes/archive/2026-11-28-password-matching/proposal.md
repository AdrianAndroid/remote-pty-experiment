# 配对改成密码匹配（取消双向同意弹窗）

## 为什么

现在的流程是「点对方 → 对方窗口弹「通话邀请」→ 他点同意 → 建房」。
用户明确不要这一步：控制端点进去、输一次密码，就应当直接一对一，不该惊动对方。

## 改成什么

- 每个**客户端**有自己的通话密码，默认 `admin123`，在设置里可改。
- 控制端点一台设备的卡片 → 弹输入框 → 输对密码 → relay 立刻建房，
  **双方同时进工作区**，对方不需要任何操作。
- 密码错 → 只有发起端看到「密码不对」，不建立任何房间。
- 排他、强耦合、小黑屋不变：一个客户端同时只能在一个房间；
  一方断线 30 秒宽限；任一方离开/超时 → 两人一起回列表。
- 取消 `ROOM_INVITE / ROOM_ACCEPT / ROOM_DECLINE` 与邀请 TTL，
  改成 `CTL_PASSWORD`（客户端上报自己的密码）+ `ROOM_JOIN {to, password}`。

## 密码怎么存

- 客户端：`<userData>/client-password`（0600，缺省 `admin123`），主进程管读；
  连上 `/ctl` 后立刻 `CTL_PASSWORD` 上报，改密码就重报一次。
- relay：**只存 PBKDF2-SHA256 哈希**（salt = client id，120k 轮），不落盘、不记日志；
  重启后客户端重连会重报，表自然重建。
- relay 只标 `password_default`（哈希等于 `admin123` 的哈希）给 UI 提示用，
  不把密码本身回传任何一端。

## 安全边界（要说清楚）

- 默认 `admin123` 是**弱口令**，知道地址的人可以从列表里挑一台试。UI 必须显性提示
  「你现在用的是默认密码」，并且改密码入口要在同一屏可点。
- 密码是唯一的门：relay 侧仍无失败次数限制（和 token 一样），列为后续加固项。
- 仍然是应用层隔离：relay 管理员、宿主机 `ps` 能看到房间里的 PTY。

## 不做

- 不做账号体系、不做每会话密码、不做「对方确认」二次开关。
- 老客户端发 `ROOM_INVITE` 只回一句「配对已改成密码匹配，请升级」。
