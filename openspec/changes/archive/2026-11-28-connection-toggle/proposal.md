# 变更：断开连接与重新连接

## Why

客户端只有「连上」这一条路，没有「断开」的出口：

- 想暂时脱离 relay（换网络、排查、不想再收推送）时，只能关掉整个窗口。
- 反过来更需要的是**断开之后还能回来**。现在一旦断开就没有任何入口重建连接，只能退出应用重开。

主进程其实已经有 `relay.disconnect()`，但渲染层没有按钮，断开后也回不到工作区 —— 能力在半路上断掉了。

## What Changes

### 客户端主进程

- `RelayClient.disconnect()` 补全清理：数据通道、字节缓冲、ready 集合、序号表、节点离线定时器、节点表一并复位，避免重连后残留旧状态。
- 新增 `RelayClient.reconnect()`：用已保存的地址与 token 重连，不需要用户重新输入。
- 新增 IPC `relay:reconnect`，preload 暴露 `window.rpty.reconnect()`。

### 渲染层

- 侧栏底部新增**「断开连接」按钮**（`⌘⇧D`），与「可操作 / 只读」并排，常驻可见。
- 断开后清空标签并回到连接页，连接页进入「已断开」态：说明 PTY 仍在宿主机上运行，按钮文案变「重新连接」，点一下就用保存的配置连回去。
- 重连成功后照常拉 `SESSION_LIST`，宿主上还活着的会话以镜像方式重新挂回来；归属仍按 `client-id` 认领，不会因为重连变成「共享」。
- 菜单「视图」增加「断开连接 ⌘⇧D」，跟按钮走同一条逻辑。

## 语义

| 动作 | 对 PTY 的影响 | 对其它端的影响 |
| --- | --- | --- |
| 断开连接 | 无，PTY 继续在宿主上跑 | 无，其它控制端不受影响 |
| 重新连接 | 无，认领原来的会话 | 无 |

断开不是 kill，也不是某一块终端的 detach —— 它是**整台客户端退出链路**，所以标签一起清掉，重连后按宿主现状重建。

## 边界

- 断开期间宿主上新建的会话，重连后照常出现在列表里。
- 断开期间自己开的终端如果被别的端 kill 掉，重连后不会出现（符合 kill 语义）。
- 断开时正在输入的字符丢弃，不排队重发。

## 验收

- 点「断开连接」→ 侧栏消失、回到连接页，页面显示「已断开」，relay 侧 `ctls` 减 1。
- 点「重新连接」→ 恢复在线，`ctls` 加 1，宿主上原有 8 个会话重新出现且标签不重复。
- 断开后再重连的标签归属仍正确（自己开的无标，别人的带「共享」）。
- 全程宿主上的 PTY 进程不中断（`ps` 里 shell pid 不变）。
