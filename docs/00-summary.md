## 1. 一句话

**在家用公司 Mac 的 CLI，不依赖 SSH，不装任何隧道二进制，云主机看不到内容。**

---

## 2. 四条硬约束

| 约束 | 来源 | 影响 |
| --- | --- | --- |
| 公司 Mac 上 `frpc` 一启动就被杀 | 用户实测 | 排除所有外部隧道程序（frp / chisel / tailscale / ttyd） |
| 两端都是 Mac（Intel + Apple Silicon） | 事实 | 排除需分架构编译的产物，用纯 Python |
| 两端都只能出站 443 | 事实 | 不监听端口，只做主动连接 |
| 必须能用 `vim` / `htop` | 目标 | 必须有真 PTY，不能是"执行命令回传输出" |

---

## 3. 环境已验证（2026-11-27 实测）

在**家里那台** Intel Mac mini（macOS 15.8.3 / x86_64，序列号 C07HL0ADPJJ9，非 MDM 托管）上跑过：

| 假设 | 结果 |
| --- | --- |
| 有能跑 asyncio 的 Python | ✅ 3.12.11 |
| 能装 `websockets` | ✅ 17.4，1.3 秒（走中科大镜像） |
| 能起 WS 服务端、二进制帧正常 | ✅ |
| 有真 PTY | ✅ `/dev/ttys009`，不是 pipe |
| 中文不乱码 | ✅ |
| 能装 `cryptography` | ✅ 50.0.2 |
| X25519 + HKDF | ✅ |
| **出站 wss 到公网** | ✅ **三个国外 echo 服务全通** |
| 有强制代理 | ✅ 无 |

**结论：架构层面可行，没有否决项。**

唯一未验证：EDR 在长时间运行时会不会杀 python 进程。这项只能部署后空转 30 分钟观察，且有退路（改进程名 / 换端口 / 加延时）。

## 4. 最终形态

```
   家 Mac ═══ wss:443 ═══▶ 云主机 relay ═══ wss:443 ═══▶ 公司 Mac
   同构 peer              在线表 + 配对              同构 peer
   一份程序                ~200 行                    一份程序
```

- **服务端**只做交换机：知道谁在线、把两条连接接上，然后变成纯字节管道
- **客户端**是同构节点：每台都能当宿主、都能当控制方
- **会话数据**（PTY、ring buffer、文件）全部在宿主机器上

---

## 5. 核心决策（12 条）

| # | 维度 | 决策 |
| --- | --- | --- |
| 1 | 拓扑 | **一对一**，两个节点一条链路 |
| 2 | 建链 | **单向**：谁点击列表谁发起 |
| 3 | 使用 | **双向**：链路通了，各自都能开通道 |
| 4 | 服务端 | 在线表 + DIAL 信令 + 字节桥接，零业务数据 |
| 5 | 客户端 | **一份程序**，无 `--role`，两端完全同构 |
| 6 | 连接 | **双连接**：`/ctl` 走 JSON 信令，每个终端一条 `/d/<token>` 走二进制 |
| 7 | 通道 | v1 只做 `shell`；`file` / `forward` 后补 |
| 8 | 加密 | v1 只有 wss（中继可见明文）；v1.5 加 E2E |
| 9 | 身份 | `node_id = SHA256(pubkey)[:8]`，relay 校验 pubkey 绑定，名字不可抢 |
| 10 | 权限 | ACL 白名单 + 方向判定 + PSK 验证，三层正交 |
| 11 | 会话 | 宿主侧 broker，ring buffer 保留最近输出，断线不杀 shell |
| 12 | 部署 | **Docker（host 网络）+ 1Panel-openresty 443**，独立 vhost + Let's Encrypt |

**第 6 条改回双连接的理由**（2026-11-27 复评）：单条 ws 在多个终端并行时会队头阻塞——一个标签跑 `cat 大文件` 产生的 10 MB 输出会把按键回显和心跳堵在队列后面。双连接让每个终端各自一条管道，天然隔离，且 relay 仍不解析帧体，总行数不变。`docs/15` 的原设计是对的。

**第 12 条的演进**：早期写"单容器 + Caddy"，实测发现 443 已被 1Panel-openresty 占用且其已具备 WS 反代三件套，Caddy 无必要；容器化保留（统一到 1Panel 的管理入口），但改为 `network_mode: host` + 源码挂载，日常发布只需覆盖文件 + `docker restart`。

## 6. 密码与权限规则

```
   建链        不需要密码    ← 谁发起谁就能连
   正向控制    不需要密码    ← 我主动连你，你同意了，我能开 shell
   反向控制    需要密码      ← 你是被动方，不能反过来控制我
   反向开通道  需要人工确认  ← 密码是技术门槛，确认是人的门槛
```

| 谁想开 shell | ACL | 我是发起方 | PSK 已验证 | 结果 |
| --- | --- | --- | --- | --- |
| 发起方 → 被动方 | ✓ | ✓ | 任意 | 允许 |
| 被动方 → 发起方 | ✓ | ✗ | ✓ | 允许 |
| 被动方 → 发起方 | ✓ | ✗ | ✗ | 拒绝 `need_psk` |
| 任意方向 | ✗ | 任意 | 任意 | 拒绝 `denied` |

**密码不是门禁，是提权凭据。**

## 7. 数据边界

| 数据 | 位置 | relay 可见 |
| --- | --- | --- |
| 终端内容、ring buffer、PTY | 宿主内存 | v1 可见（明文帧）→ v1.5 不可见 |
| 文件、私钥、ACL | 各自本机 | 否 |
| 谁在线、哪两条连接配对 | relay 内存 | 是（重启即丢） |

**v1 是唯一的明文窗口期**，所以 v1 只在家里/公司自己的网络里跑，不做公开部署。

---

## 8. 分期

客户端按"先验手感、再接网络、最后打包"推进，每一阶段都能独立跑起来。

| 版本 | 内容 | 预计 |
| --- | --- | --- |
| **P0** | 单窗口 + 本地 xterm + 本地 zsh，只验手感（无网络） | 半天 |
| **P1** | main 进程持有 PTY、多会话 broker、ring buffer、重连重放、本地 IPC 帧协议 | 1–2 天 |
| **P2** | 接 relay：双连接、信令、ACL、多终端异地打通 | 2–3 天 |
| **P3** | 打包 DMG、bundle id、签名、开机自启 | 1 天 |
| **v1.5** | E2E 加密（X25519 + HKDF）、PSK、方向权限、多设备并行 | 2–3 天 |
| **v2** | `file` / `forward` 通道、分屏、自举发布 | 待定 |

**v1 的验收标准**：家里连着公司，同时开 3 个终端互不干扰，能跑 `vim`、`htop`、`top`，`ctrl+C` 正常，改窗口大小不花屏，断网 10 秒后自动恢复且不丢历史。

---

## 9. 明确不做（v1）

多设备并行（同时连两台机器）、分屏、会话迁移、WebRTC 打洞、共享终端（多人看同一会话）、图形界面转发、移动端 App、自动更新。

其中「多设备并行」与「分屏」在 v1.5 再做，v1 的数据结构（`PaneNode`、按设备分组的会话表）已为其留位。
