# 30 · 断开连接与重新连接

## 之前缺什么

客户端只有「连上」一条路。主进程里其实早就写好了 `RelayClient.disconnect()`，但：

- 渲染层没有任何入口能调到它。
- 就算调到了，界面会停在「relay 已断开」的横幅上，标签还在、画面死了，**没有重新连接的按钮**，只能退出应用重开。

能力只做了一半 —— 断得掉，回不来。

## 现在是什么

侧栏底部，紧跟「可操作 / 只读」下面，多了一行常驻的**「断开连接 ⌘⇧D」**（红点，悬停变红）。点它：

1. 关掉 ctl 与所有数据通道，`manualClose = true`，自动重连定时器清掉 —— 不会自己偷连回去。
2. 本地状态全清：字节缓冲、ready 集合、序号表、节点离线定时器、节点表、hostname。
3. 标签清空，回到连接页，页面进入「已断开」态：一句话说明宿主机上的终端还在跑，一枚「重新连接」按钮，下面一行小字「修改地址或 token」可以展开完整表单。

点「重新连接」→ 主进程用**已保存的** url 与 token 走 `relay.connect()`，渲染层不发一个字的配置。

## 语义

| 动作 | PTY | 其它控制端 | 本端标签 |
| --- | --- | --- | --- |
| 断开连接 | 不动，继续跑 | 不受影响 | 全部清掉 |
| 重新连接 | 不动，认领原会话 | 不受影响 | 按宿主现状重建 |

断开 ≠ kill，也 ≠ 单块终端的 detach。它是**整台客户端退出链路**，所以标签一起清 —— 留着旧 leafId，重连后 relay 再推一遍列表就会撞出重复标签。

## 实测（2026-11-28，mini 上 A/B 两窗口 + MBP）

**镜像端（B，9223）**

- 断开前 `ctls 3 / viewers 24` → 断开后 `ctls 2 / viewers 16`，标签 8 → 0，页面显示「已断开与 relay 的连接」。
- 重连后 `ctls 3 / viewers 24`，8 个标签全部回来，带「共享」（B 不是创建端，归属正确）。
- 输入 `echo AFTER-RECONNECT shell=$$` → `AFTER-RECONNECT shell=80327`，与断开前 `HOST-CHECK ... pid=80327` 是同一个 pid，**PTY 全程没断**。

**创建端（A，9222，primary）**

- 断开 → 重连后 8 个标签仍在，且**全部没有「共享」标记**，说明 `client-id` 的归属认领在重连后仍然有效。

## 坑与取舍

- **标签必须清**。断开只是本端不看，relay 那边的会话还在；如果本地留着 leafId，重连后 `SESSION_LIST` 会再 adopt 一批新 leafId，同一块 PTY 会出现两个标签。
- **重连必须走 `connect()` 而不是裸 `openCtl()`**。`connect()` 会先把 `manualClose` 复位、清重连定时器、关旧 ctl，幂等；直接开 socket 会留下两条 ctl。
- **断开期间的变化以宿主为准**。断开时新建的会话重连后会出现；断开期间被 kill 的不会出现 —— 这跟 kill 语义一致，不做「本端记忆」。
- 断开时正在输入的字符丢弃，不排队重发（排队等于重连后往别人屏幕里塞东西）。
