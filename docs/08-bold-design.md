## 0. 一句话

把项目从「用 WebSocket 复刻 SSH」重新定位为「**云主机全程盲中继的个人终端基础设施**」——

云主机不知道你在做什么，断线不丢会话，一条连接同时承载终端、文件与端口。

## 1. 三个跃迁

```
       保守版                                   大胆版
┌──────────────────────┐              ┌──────────────────────────────┐
│ TLS 到 nginx 终结     │   ────▶     │ 应用层 E2E 加密，云主机只转发密文 │
│ 云主机能看到明文 shell │              │ 云主机被入侵也拿不到内容          │
└──────────────────────┘              └──────────────────────────────┘
┌──────────────────────┐              ┌──────────────────────────────┐
│ 一条连接只干终端       │   ────▶     │ 多路复用：shell/文件/转发/剪贴板 │
│ base64 JSON 帧        │              │ 二进制帧 + 8 字节头，省 33% 带宽  │
└──────────────────────┘              └──────────────────────────────┘

│ 断线 = 新 shell        │   ────▶     │ Session Broker：连接与 PTY 解耦 │

└──────────────────────┘              └──────────────────────────────┘
```

## 2. 跃迁一：盲中继（应用层端到端加密）

### 问题

保守版里 TLS 在 nginx 终结，relay 拿到的是**明文 shell 流量**。这意味着：

- 云主机被入侵 → 你的全部终端内容泄露
- 云主机运维方（包括你自己某天租的便宜 VPS）理论上可抓包
- token 泄漏 → 直接拿到 shell

对一个要长期承载公司工作内容的通道，这是真实缺陷，不是理论洁癖。

### 方案

在 WebSocket 之上叠一层 Noise 风格握手，两端协商出会话密钥，`data` 载荷全程 ChaCha20-Poly1305：

```
agent                                          terminal
  │  ── hello {eph_pub_A, static_id_A} ──▶        │
  │  ◀── hello {eph_pub_B, static_id_B, mac} ──   │
  │  ── finish {mac} ──▶                          │
  │                                               │
  │  X25519(eph_A, eph_B) → HKDF → K_session      │
  │                                               │
  │  ═══ 之后所有帧：AEAD(K_session, nonce++, pt) ═══
  ▼                                               ▼
              relay 只看到密文，长度 + 时间
```

要点：

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 密钥协商 | X25519 ECDH（ephemeral + static） | 前向保密；static 用于身份认证 |
| 对称加密 | ChaCha20-Poly1305 | 移动端与无 AES 加速环境友好；AEAD 自带完整性 |
| 身份认证 | static key 双方预共享（配对时录入） | 比 token 强：+token 只能"连上"，不能"冒充" |
| nonce | 单调计数器，双向分离 | 防重放 |
| 实现 | `cryptography` 库 | 不自研密码学 |

### 收益

- 云主机变成**哑管道**：即使 root 被拿下，也只能看到加密字节流
- 鉴权从"知道 token"升级为"持有私钥"
- 不再需要 TLS 之外的额外防护假设

### 代价

- agent 与 terminal 各多约 150 行握手与加解密
- 调试变难：抓包里全是密文（提供 `--no-crypto` 仅本地测试开关）
- 多一个依赖：`cryptography`（比 `websockets` 重，公司机安装风险上升）

> **这一条是全稿里我最推荐的**。它把一个"技术上能跑"的方案，变成"敢长期用"的方案。

## 3. 跃迁二：多路复用通道

### 问题

保守版一条 wss 只承载 shell。要传文件、要临时转发一个端口、要同步剪贴板，都得另开机制。

### 方案：8 字节头 + 二进制帧

```
 0        1        2        3                7
┌────────┬────────┬──────────────┬──────────────────┐
│ ver(1) │type(1) │ channel(2)   │ length(4, BE)    │
└────────┴────────┴──────────────┴──────────────────┘
                     ↓
              payload (length 字节)
```

| type | 名称 | 方向 | 说明 |
| --- | --- | --- | --- |
| 0x01 | HELLO | 双向 | 握手 |
| 0x02 | DATA | 双向 | 通道数据 |
| 0x03 | WINDOW | 双向 | 流控（每通道 256 KB 窗口） |
| 0x04 | OPEN | 双向 | 开新通道 `{channel, kind, params}` |
| 0x05 | CLOSE | 双向 | 关通道 |
| 0x06 | RESIZE | T→A | 终端尺寸 |
| 0x07 | SNAPSHOT | A→T | 屏幕快照回放 |
| 0x08 | CLIPBOARD | 双向 | 剪贴板 |
| 0x09 | PING | 双向 | 心跳 |

channel kind：

| kind | 用途 |
| --- | --- |
| `shell` | 一个 PTY 会话 |
| `file` | 文件传输（复用 SFTP 语义的子集：get/put/ls/stat） |
| `forward` | 端口转发（TCP over channel） |
| `exec` | 一次性命令（保留 webhook 时代的能力） |

### 为什么值得

一旦有了 channel，**这个项目就不再是"终端工具"，而是"我的 SSH"**：

- 家端 `vscode` 的 Remote 走 `forward` 通道
- 传文件不需要 `scp`，走 `file` 通道还带进度
- 临时把公司机的 `:3000` 映射到家端，走 `forward`

### 关键代价

流控是最容易写错的部分。每个 channel 独立窗口，接收方消费后回 `WINDOW` 帧。**不做流控**的话，`cat 大文件` 会把家端浏览器内存打爆——这是必须做的，不是可选项。

### 相对保守版的修正

同时推翻 ADR-002（base64 JSON）：

| | base64 JSON | 二进制 8 字节头 |
| --- | --- | --- |
| 体积 | +33% | 0 开销 |
| 解析 | `json.loads` | `struct.unpack`，快 5–10 倍 |
| 调试 | 肉眼可读 | 需 `xxd` |
| 浏览器 | 直接可用 | `ArrayBuffer`，稍绕 |

结论：**生产走二进制，`--debug-json` 开关保留人类可读模式**。

## 4. 跃迁三：Session Broker（连接与 PTY 解耦）

### 问题

保守版断线 = 杀 PTY = 重连是新 shell。靠 tmux 打补丁，但：

- tmux 有自己的前缀键、有自己的状态栏，与远程终端体验打架
- tmux 不解决"重连后看到的是空白"的问题

### 方案：agent 常驻 broker，PTY 生命周期独立

```
agent daemon (常驻)
  │
  ├─ session "main" (PTY 已 spawn, zsh 在跑)
  │     ├─ screen model (vt100 状态机, 保留最后 2000 行)
  │     └─ output ring buffer (最后 64 KB 原始字节)
  │
  ├─ ws 连接 #1  ← attach → 收到 SNAPSHOT + ring buffer → 正常流
  ├─ ws 断开     ← detach → PTY 继续跑，输出继续进 ring buffer
  └─ ws 连接 #2  ← attach → 瞬间看到断开前的完整画面
```

### 屏幕快照怎么实现

两种路线：

| 路线 | 实现 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 字节回放 | 保存最近 64 KB 原始输出，attach 时整段重放 | 简单（`ringbuffer`） | 远端程序在期间可能已移动光标，重放后画面可能与实际位置不一致 |
| B. 屏幕模型 | 内置 vt100 解析器，维护 2D 字符网格 + 光标 + 属性 | 精确还原 | 需要实现一个终端模拟器（约 500 行） |

**推荐 A 起步，B 作为终态**。A 在 95% 场景（`ls`、`git`、编译输出）完全够用，出错也只影响全屏程序重连后的一次画面。

### 附加能力：会话命名与多会话

```
session list:
  main   zsh     running   2h13m   detached
  build  bash    running   0h04m   attached(1)
```

家端可以 `attach main` / `attach build`，协议层加一个 `session_id` 参数即可。

### 这一条的战略意义

做完这一层，**agent 就有了"服务器"的属性**，不再是一个被动脚本。后续所有能力都可以挂上去：定时任务、webhook 触发器、状态面板。

## 6. 怎么开发（这是本稿更重要的部分）

### 6.1 核心原则：协议与传输分离，让 80% 的开发不依赖公司网络

最大的开发摩擦不是写代码，是**每次改动都要跑到公司机上去验证**。解法是把协议做成纯逻辑：

```
protocol/          纯函数 + 状态机，零 I/O
  ├─ frames.py     encode/decode（字节 ↔ 帧对象）
  ├─ mux.py        通道状态机、流控窗口
  ├─ crypto.py     握手与加解密（可注入假密钥）
  └─ session.py    会话状态机

transport/         注入式接口
  ├─ memory.py     本地内存对连（测试用）
  ├─ ws.py         WebSocket
  └─ loopback.py   本地 TCP（模拟公网）
```

这样 `pytest` 里可以一条命令跑完整链路：

```python
a, b = make_memory_pair()
sess = Session(a); sess.spawn_shell()
b.send(encode_data(ch, b"ls\r"))
assert b"file.txt" in read_until(b, b"$")
```

**目标：90% 的逻辑测试在本地 3 秒内跑完。**

### 6.2 三级测试金字塔

| 层 | 内容 | 频率 | 依赖 |
| --- | --- | --- | --- |
| L1 单元 | 帧编解码、AEAD、流控窗口、状态机转换 | 每次保存 | 无 |
| L2 集成 | 本地 relay + agent + fake terminal 三进程 | 每次提交 | localhost |
| L3 真机 | 家 → 云 → 公司 全链路 | 每阶段 | 全部环境 |

L3 只验证"环境相关"的事（NAT、网关、证书、launchd），不验证逻辑。逻辑问题必须在 L1/L2 拦下。

### 6.3 混沌测试（这个项目必须有）

断线是这个项目的**常态**，不是异常。所以要把"断"当成一等公民来测：

```python
# 测试：随机断连 100 次，会话不丢
for i in range(100):
    transport.kill()
    await reconnect()
    assert session.alive
    assert screen.restored
```

注入点：`transport` 层随机丢弃 / 延迟 / 半关闭。用 `hypothesis` 或手写 `ChaosTransport`。

### 6.4 协议一次性定型，不要 v1/v2 反复

前面保守版设了 v1（base64 JSON）→ v2（二进制）的路径。这是**错误的开发策略**：协议改动成本最高，改一次要动两端 + 部署 + 联调。

建议：**用一天时间把协议 v1 直接按终态设计（二进制 + mux + crypto 字段预留）**，第一个可运行版本就是终态格式。宁可第一次多花半天，也不要经历三次协议迁移。

### 6.5 用"可观测性"驱动开发

终端类项目最难的是"看不见的内部状态"。从第一天就加：

- `--debug-frames`：打印每个帧的 type/channel/len（不打印 payload）
- `/metrics`（relay）：连接数、上下行字节、帧率、重连次数
- 家端状态条：`connected · 32ms · ch=4 · 1.2MB↑ 340KB↓`

有了这些，调 `resize` 花屏这种问题不用靠猜。

### 6.6 代码组织（按可替换性分层，不按功能分）

```
remote-pty-experiment/
├── protocol/          # 纯逻辑，无 I/O，全部可单测
├── transport/         # 可替换：memory / ws / loopback
├── agent/             # broker + session + pty
├── relay/             # 云主机
├── client/            # 本地 CLI
├── web/               # 浏览器
├── tools/             # 调试工具：wscat 替代、帧解码器
└── tests/             # L1 / L2 / chaos
```

关键：**`protocol/` 不 import 任何网络库**。这条约束一旦破坏，单测就跑不动了。

## 7. 重排后的里程碑

砍掉保守版的"M1 行模式"——那是一次性代码，验证完就要扔，不如直接把 PTY 做进去。

| 阶段 | 内容 | 工期 | 验证标准 |
| --- | --- | --- | --- |
| P0 | `protocol/` 帧编解码 + mux 状态机 + 单测 | 0.5d | `pytest` 全绿，覆盖 encode/decode 往返 |
| P1 | 内存 transport + 假 PTY + 会话状态机 | 0.5d | 内存里能跑通 `ls` 交互 |
| P2 | relay + agent + 网页终端，localhost 打通 | 1d | 本机三进程能看到真实 shell |
| P3 | 换真 PTY（forkpty）+ resize | 0.5d | `vim` / `htop` 正常 |
| P4 | 部署到云主机，公司机联调 | 1d | 异地真实可用 |
| P5 | E2E 加密 | 0.5d | `--no-crypto` 与加密两种模式互通 |
| P6 | Session Broker + ring buffer 回放 | 1d | 拔网 5 分钟重连，画面与进程都在 |
| P7 | 流控 + 文件通道 | 1d | 传 1 GB 文件不 OOM |
| P8 | 菜单栏 App 外壳 + 一键启停 | 1d | 托盘有状态灯，点一下连上 |

总计约 **7 个工作日**，比保守版的"M1–M5"更紧凑——因为省掉了两次协议迁移和一次行模式返工。

## 8. 大胆项的取舍表

| 大胆设计 | 收益 | 成本 | 风险 | 建议 |
| --- | --- | --- | --- | --- |
| E2E 加密 | 云主机变哑管道，敢长期用 | 150 行 | `cryptography` 依赖体积 | **必做** |
| 二进制帧 | 省 33% 带宽，解析快 | 半天 | 调试变难 | **必做** |
| 多路复用 + 流控 | 从终端工具升维成 SSH 替代 | 2 天 | 流控易写错 | 做，但流控放 P7 |
| Session Broker | 断线不丢会话 | 1 天 | PTY 泄漏、孤儿进程 | **必做** |
| 屏幕快照回放（字节版） | 重连有画面 | 0.5 天 | 全屏程序可能错位 | 做 |
| 屏幕模型（vt100 解析器） | 精确还原 | 3 天 | 维护一个终端模拟器 | 先不做 |
| 文件通道 | 替代 scp | 1 天 | 大文件要流控 | 做 |
| 端口转发通道 | 替代 ssh -L | 0.5 天 | 安全面扩大 | 做，但默认关闭 |
| 菜单栏 App | 体验闭环，一键开关 | 1 天 | Swift 开发 | 做 |

## 9. 刻意不做的"大胆"

| 想法 | 为什么不 |
| --- | --- |
| WebRTC 打洞直连 | 两端 NAT + 公司网关，成功率低；引入信令服务器，复杂度翻倍；且 p2p 流量特征更可疑 |
| 自研加密算法 / 自实现 AES | 绝对不做 |
| 多用户 / 权限系统 | 个人场景，收益为零，复杂度极高 |
| 移动端 App | 手机打字跑 `vim` 是伪需求 |
| 图形化桌面转发（VNC） | 与本项目定位冲突，走别的工具 |
| 用 Rust 重写全部 | 性能不是瓶颈，PTY I/O 是；重写只会拖慢交付 |

## 10. 如果只能做三件事

按投入产出排序：

1. **E2E 加密**（半天）：这是"敢不敢长期用"的分水岭。没有它，云主机上跑着明文 shell 这件事会一直让你心里不踏实。
2. **Session Broker + 字节回放**（一天半）：断线重连后回到原会话、看到原画面——这个体验差异比任何性能优化都明显。
3. **协议一次性定型为二进制 + mux**（半天）：避免三次协议迁移，省下的返工时间远超设计时间。

其余都是锦上添花。
