# 12 · 概念模型与术语表

这一篇固定概念。后面所有讨论和代码都按这里的定义走，避免"角色""端""会话"三个词混用。

---

## 1. 三层结构

```
   ┌─────────────────────────────────────────────────────────────
   │  1 个服务端 · relay
   │     职责：在线表 / DIAL 信令 / 桥接字节
   │     不知道：谁要 shell、谁要文件、内容是什么
   ├─────────────────────────────────────────────────────────────
   │  N 个客户端 · peer（同一份程序，同构，无差别）
   │     office-mini · home-mbp · home-nas …
   │     每个 peer 都同时具备两种能力：当宿主、当控制方
   ├─────────────────────────────────────────────────────────────
   │  任意两个 peer 之间 · bridge（一条隧道）
   │     桥上是若干条 channel，每条 channel 有独立的宿主与控制方
   └─────────────────────────────────────────────────────────────
```

**不是"两种客户端连服务器"，而是"若干同构节点连交换机，两两建桥，桥上开通道"。**

---

## 2. 角色是关系，不是身份

| | 错误理解 | 正确理解 |
| --- | --- | --- |
| 角色属于 | 进程 / 安装包 / 启动参数 | **每一条 session** |
| 数量 | 一台机器只有一个角色 | 一台机器可以同时是若干会话的宿主、若干会话的控制方 |
| 变化 | 启动时确定，运行期不变 | 每开一个通道确定一次 |

关系型数据库的类比：不是两张表（agent 表 + client 表），而是**一张 session 表，带 `host_id` 和 `controller_id` 两个外键**。

```
   sessions
   ┌──────────────┬────────────────┬─────────────────┬──────────┐
   │ session      │ host_id        │ controller_id   │ kind     │
   ├──────────────┼────────────────┼─────────────────┼──────────┤
   │ main         │ office-mini    │ home-mbp        │ shell    │
   │ home         │ home-mbp       │ office-mini     │ shell    │
   │ nas-backup   │ home-nas       │ office-mini     │ file     │
   └──────────────┴────────────────┴─────────────────┴──────────┘
```

同一台 `home-mbp`：在 `main` 里是控制方，在 `home` 里是宿主。**两行同时成立，不冲突。**

---

## 3. 一条桥上的完整视图

```
   home-mbp ═══════════════════════════════════════════════ office-mini
            │ ch  0x0001   shell(main)      A 控制 B 的 shell │
            │ ch  0x8001   shell(home)      B 控制 A 的 shell │
            │ ch  0x8002   file             B 读 A 的文件     │
            └──────────────────────────────────────────────────┘
```

| channel | 宿主 | 控制方 | 谁 spawn 了 PTY |
| --- | --- | --- | --- |
| `0x0001` | office-mini | home-mbp | office-mini |
| `0x8001` | home-mbp | office-mini | home-mbp |
| `0x8002` | home-mbp | office-mini | 无 PTY（文件通道） |

channel id 高 1 位 = 发起方。**发起方 = 控制方 = 发 OPEN 的那一端。**

---

## 4. 代码里怎么落

一个 peer 进程内部有两张表，各管一个方向：

```
   peer 进程
   ├── Broker    「我是宿主的那些会话」
   │      session_id → { PTY fd, ring buffer, 当前接入的 channel 列表 }
   │      职责：spawn / 保活 / 记录输出 / 断线后继续跑
   │
   └── Remote    「我是控制方的那些会话」
          session_id → { 对端 node_id, channel, 终端尺寸 }
          职责：发输入 / 渲染输出 / 断线重连
```

**两张表在同一个进程、同一个事件循环里。** 所谓"宿主角色"就是 Broker 里有条目，所谓"控制方角色"就是 Remote 里有条目。

不需要"切换到宿主模式"，也不需要"启动成服务端"。

## 5. 会话与通道的区别（最容易混的一对）

```
   session   ── 活在宿主机器上，有独立生命周期
       │        断线它还在跑，输出继续进 ring buffer
       │
       │ 被接入
       ▼
   channel   ── 传输层的逻辑管道，随连接建立 / 销毁
       │        一条 session 未来可被多条 channel 同时接入（共享终端）
       │
       │ 跑在
       ▼
   bridge    ── 两条 ws 的配对，两端各一个 socket
```

| | session | channel | bridge |
| --- | --- | --- | --- |
| 存在于 | 宿主机器 | 两端内存 | relay 内存 |
| 断线后 | **存活** | 销毁 | 销毁 |
| 生命周期由谁决定 | 用户（`exit`） | 连接 | DIAL |
| 数量关系 | 1 : N | N : 1 | 1 : 1 |

一句话：**session 是"活的东西"，channel 是"看它的管子"。**

## 6. 术语表

| 术语 | 定义 | 不要混用 |
| --- | --- | --- |
| **relay** | 云主机上的交换机：在线表 + 信令 + 字节桥接 | ≠"服务器"（它不服务业务） |
| **peer** | 任意一个对等节点，同一份程序 | ≠"客户端"（这个词暗示被动） |
| **node_id** | `SHA256(静态公钥)[:8].hex()`，节点身份 | ≠主机名（可改，不可信） |
| **bridge** | 两条 ws 的配对，位于 relay | ≠隧道软件 |
| **channel** | 桥上的一条逻辑通道，带方向位 | ≠连接（连接是 bridge） |
| **session** | 宿主机器上的一个 PTY 生命周期 | ≠channel（session 断线不死） |
| **host / 宿主** | 提供资源的一端：spawn PTY、提供文件、发起 TCP | ≠服务器 |
| **controller / 控制方** | 发 OPEN 的一端 | ≠客户端 |
| **kind** | 通道类型：`shell` / `file` / `forward` / `exec` | |
| **ring buffer** | 宿主侧保存最近 64 KB 输出，供重连回放 | ≠日志 |
| **ACL** | 本机白名单，控制谁能连、能开什么 kind | ≠relay 的职责 |

## 7. 如果反过来做会怎样

假设按"两种客户端"实现：

```
   ✗ 方案 A：两个程序
        rpty-host      部署在公司机
        rpty-control   部署在家机
     → 公司机想反向取家里文件，得再装一个 rpty-control
     → 三台机器要装 3 份，配置 3 次
     → 代码分叉，两套 bug

   ✗ 方案 B：一个程序 + 启动参数 --role=host
     → 运行期不能反转，想反向必须重启换模式
     → 同一条桥上无法同时存在双向会话
     → 等于把固定角色换个名字保留下来
```

正确做法：

```
   ✓ 一份程序，无 --role 参数
     启动即在线，同时能接客、能连人
     方向由每次 OPEN 决定
     默认接不接客由 ACL 决定（不是由程序形态决定）
```

---

## 8. 一句话总结

> 服务端是**交换机**，客户端是**同构节点**，
> 宿主与控制方是**每条会话上的关系**，不是机器的属性。
