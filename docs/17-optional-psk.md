# 17 · 可选密码与 TOFU 信任

在 `docs/16-password-and-psk.md` 的 PSK 基础上，把密码变成**可选项**：

```
   设了密码   →  点击列表时验证密码（可记住）
   没设密码   →  直接连接
```

这篇说明：怎么做到"没密码也能连"，而**内容始终是密文**。

---

## 1. 唯一不能让步的原则

| 做法 | 判断 |
| --- | --- |
| 没密码 = 不加密，明文过 relay | ✗ **绝对不能** |
| 没密码 = 匿名 ECDH 加密 | ✓ 可以 |
| 没密码 = 不允许连接 | 太严，违背需求 |

原因很简单：relay 在 TLS 终结处。一旦 data 连接是明文，云主机就能看到你终端里的每一个字——这正是整个项目从第一天起要解决的事。

**所以：密码可选，加密不可选。**

---

## 2. 没密码时，密钥从哪来

| 方案 | 密钥来源 | relay 能解开吗 | 能防中间人吗 |
| --- | --- | --- | --- |
| 用 `pair_id` 派生 | relay 生成的串 | **能** | ✗ |
| 用两个 `node_id` 派生 | 公开信息 | **能** | ✗ |
| **临时 X25519 ECDH** | 两端各出临时密钥 | ✗ | 部分（见下） |
| ECDH + 静态密钥签名 | 同上 + 身份证明 | ✗ | ✓ |

前两种是陷阱：看着"有密钥"，其实 relay 能算出来，等于没加密。

**正确做法是临时 ECDH**——两端各自生成一对临时密钥，交换公钥，各自算出同一个共享秘密。relay 在中间只能看到公钥，算不出共享秘密。

---

## 3. 因此需要一对静态密钥（但用户完全无感）

ECDH 只能保证"内容不被偷看"，不能保证"对方是谁"——中间人可以跟两边各做一次 ECDH。

解决：每台机器首次运行时**自动生成一对 X25519 静态密钥**，`node_id = SHA256(公钥)[:8]`。

```
   用户要做的：           0 件事
   程序自动生成：          ~/.rpty/identity（权限 600）
   node_id 怎么来：       公钥哈希，天然无法伪造
   首次连一台新机器：       显示对方指纹，确认一次，之后记住（TOFU）
```

这就是 SSH 的 `known_hosts` 模型，业界用了二十多年：

```
   第一次连 office-mini
   ┌──────────────────────────────────┐
   │  首次连接 a3f2c1d8               │
   │  指纹 A3:F2:C1:D8:4E:...         │
   │  与对方屏幕上的值一致吗？          │
   │  [ 信任并记住 ]  [ 取消 ]          │
   └──────────────────────────────────┘
```

**这一步不是负担，而是让"无密码"变得安全的前提。**

---

## 4. 三档信任级别

| 模式 | 密钥 | 认证 | 内容保密 | 防中间人 | 防私钥被盗 |
| --- | --- | --- | --- | --- | --- |
| **基础**（默认，无密码） | ECDH + 静态密钥签名 | TOFU 指纹 | ✓ | ✓ | ✗ |
| **密码**（可选） | ECDH + 签名 + **PSK 混合** | TOFU + 暗号 | ✓ | ✓ | ✓ |
| ~~明文~~ | 无 | 无 | ✗ | ✗ | ✗ |

差别只在最后一列：**设了密码，即使哪天私钥文件被复制出去，没有密码也解不开。**

这是密码真正的价值——不是"要不要加密"，而是"多一道只有你知道的熵"。

---

## 5. 密码怎么用（比 16 更严谨）

`docs/16` 里给的是"PSK 直出密钥"（40 行，简单）。加上 ECDH 之后，两段熵合并：

```python
# 握手（都带签名，身份先验）
#  A → B: {from, eph_A, psk_on: true, sig_A}
#  B → A: {from, eph_B, psk_on: true, sig_B}

shared = X25519(eph_A_priv, eph_B_pub)          # 32 bytes

ikm = shared + (psk_bytes if psk_on else b"")
session_key = HKDF(SHA256, 32, salt, b"rpty-v1").derive(ikm)
```

要点：

- **`psk_on` 决定要不要把密码熵混进密钥**，两端必须一致
- 密码错了不会"校验失败"，而是**AEAD 解密失败**——因为派生出了另一把钥匙
- 签名先验通过 → 说明身份没问题；解密失败 → 说明密码不对。**两种错误能清楚分开**

这比"传密码让对方校验"优雅得多：密码从头到尾没在网络上出现过一次。

---

## 6. 握手协商与四种结果

```
   A(pwd) ──▶ B(pwd)     psk_on 一致        ✓ 正常连接
   A(pwd) ──▶ B(no pwd)  B 看到 psk_on=true  ✗ NEED_PSK_AT_A
   A(no)  ──▶ B(pwd)     A 看到 psk_on=true  ✗ 本地弹框要求输入密码
   A(no)  ──▶ B(no)      psk_on 都 false     ✓ 直接连接
```

界面必须把四种情况说清楚：

| 情况 | 提示文案 | 用户动作 |
| --- | --- | --- |
| 对方要密码 | 「对方设置了密码，请输入」 | 弹输入框 |
| 我有密码对方没有 | 「对方未设置密码，无法用密码连接」 | 提示对方去设置，或我临时关闭密码 |
| 密码错 | 「密码不匹配」 | 重输，不重试网络 |
| 一切正常 | 无提示 | 直接用 |

**"密码不匹配"和"连接失败"必须分开。** 前者重输就好，后者才需要查网络。混在一起用户会反复点击列表。

## 7. 交互流程

```
   ┌─────────────────────────────────────────────┐
   │  ● office-mini       在线                   │  ← 有密码的 peer 旁边加个 🔒
   │  ○ home-nas          离线                   │
   └─────────────────────────────────────────────┘
                    │ 用户点击
                    ▼
        ┌───────────────────────────┐
        │  连接到 office-mini        │
        │  该连接需要密码            │
        │  > *******************    │
        │  ☑ 记住密码（Keychain）    │
        │  [ 连接 ]  [ 取消 ]        │
        └───────────────────────────┘
                    │
                    ▼
             握手 → 建立 data 连接 → 进入终端
```

三个细节：

1. **锁图标**：列表上就能看出哪些 peer 需要密码，不用点进去才发现
2. **记住密码**：勾选后进 macOS Keychain，下次点击直接连，不再问
3. **取消不报错**：用户主动取消是正常操作，不该弹"连接失败"

---

## 8. 密码存在哪

| 场景 | 存放 |
| --- | --- |
| 勾了"记住" | macOS Keychain（`security add-generic-password -s rpty -a <node_id>`） |
| 没勾 | 只在内存，连接断开即丢 |
| 配置文件 | **不存密码**，只存"这个 peer 需要密码"这个标记 |

配置文件里只保留标记，密码本体进 Keychain——这样即使 `~/.rpty/config.toml` 被同步到云盘，也不会泄露密码。

```toml
[peer."a3f2c1d8"]
name       = "office-mini"
psk_required = true          # 标记而已，密码在 Keychain
perms      = ["shell", "file"]
```

## 9. 两种模式的实现规模

| 模块 | 无密码模式 | 有密码模式 |
| --- | --- | --- |
| 静态密钥与 node_id | 必需（首次生成） | 必需 |
| TOFU 指纹确认 | 必需 | 必需 |
| ECDH 握手 | 必需（~60 行） | 必需 |
| 签名验证 | 必需（~30 行） | 必需 |
| PSK 混合 | — | +15 行 |
| 密码输入 UI | — | +40 行 |

**密码只多 55 行左右。** 因为加密骨架（ECDH + 签名 + AEAD）两种模式共用，密码只是往 HKDF 的输入里多加一段。

这也说明：**先做无密码模式，加密就已经完整了**，密码是后面挂上去的一层，不是重写。

---

## 10. 一个要提前想清楚的边界

如果以后要做**多节点**，密码是"每台一套"还是"全局一套"？

| 策略 | 优点 | 缺点 |
| --- | --- | --- |
| 全局一套（前期） | 简单，只记一个 | 任一节点泄露，全线沦陷 |
| 按 peer 一套（以后） | 隔离 | 要记多个 |

配置文件结构已经留好位置（`[peer."xxx"]`），实现时从"取全局"改成"先查 peer 再回退全局"即可，不改协议。

---

## 11. 一句话

> **加密是地板，密码是门锁。**
> 没装门锁房间依然是封闭的（ECDH 保证），只是谁都能推门进来试试；
> 装了门锁，连钥匙被抄走也进不来（PSK 混合）。
> 两种都可以住，但**不能把墙拆了当门**。
