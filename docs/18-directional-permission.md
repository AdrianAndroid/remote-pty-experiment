# 18 · 方向性权限：建链 ≠ 反向控制

核心规则：

```
   建链      不需要密码    —— 谁发起谁就能连（对方 ACL 同意即可）
   正向控制  不需要密码    —— 我主动连你，你同意了，我就能开 shell
   反向控制  需要密码      —— 你是被动方，不能反过来控制我
```

这篇把这条规则落到权限矩阵和代码上。

---

## 1. 为什么这个设计是对的

原来密码是"连接门槛"：没密码不让连。
现在密码是"提权凭据"：连上了，但想反向拿控制权，得证明自己人。

```
   建链：A ──DIAL──▶ B           （不需要密码）
         A ✓ 可以开 shell 到 B
         B ✗ 不能开 shell 到 A     ← 需要密码

   配了密码：
         A ──DIAL──▶ B  (HELLO 双方验证 PSK)
         A ✓ 可以开 shell 到 B
         B ✓ 可以开 shell 到 A     ← 反向也通了
```

这个划分贴合真实心智：

- **主动连接 = 主动暴露自己**。你点了一下列表，意味着你已经知道要连谁、愿意让它连进来。所以双向都应该通。
- **被动等待 ≠ 授权对方被控制**。B 只是挂在那儿等，它不认识来访者（除了 ACL 里的 node_id），不该因此就把自己的终端交出去。
- **密码 = "我们确实是同一个主人的两台机器"** 的证据。

而且它解决了原来的一个尴尬：如果密码是连接门槛，那"只想单向用"的用户也被迫设密码。现在不用了——不设密码也能用，只是没有反向能力。

---

## 2. 权限矩阵

一次 `OPEN kind=shell` 是否放行，要过三道：

```
   ① ACL        对方 node_id 在我白名单里，且含 shell 权限
   ② 方向        我是发起方？  → 直接放行
                 我是被动方？  → 看第 ③ 条
   ③ PSK        本次握手是否完成过 PSK 验证
```

完整矩阵：

| 谁想开 shell | ACL 允许 | 我是发起方 | PSK 已验证 | 结果 |
| --- | --- | --- | --- | --- |
| 发起方 → 被动方 | ✓ | ✓ | 任意 | **允许** |
| 被动方 → 发起方 | ✓ | ✗ | ✓ | **允许** |
| 被动方 → 发起方 | ✓ | ✗ | ✗ | **拒绝 `need_psk`** |
| 任意方向 | ✗ | 任意 | 任意 | **拒绝 `denied`** |

注意第一行：**主动方即使没设密码，也能控制对方**。这正是"建链即可用"的含义。

## 3. 代码

连接上下文加两个字段：

```python
@dataclass
class Link:
    peer_id: str
    initiator: bool          # 本次连接是否由我发起
    psk_verified: bool       # 握手阶段是否完成 PSK 验证

    def check_open(self, kind: str, acl_perms: set[str]) -> str | None:
        """返回 None 表示放行，否则返回拒绝原因"""
        if kind not in acl_perms:
            return "denied"                 # ACL 没授权这类操作
        if self.initiator:
            return None                     # 我主动连的，允许
        if not self.psk_verified:
            return "need_psk"               # 被动方想反向，需要密码
        return None
```

OPEN 处理处调用它：

```python
async def on_open(link: Link, msg):
    reason = link.check_open(msg.kind, acl.perms_of(link.peer_id))
    if reason:
        await send({"type": "OPEN_ERR", "channel": msg.channel, "reason": reason})
        return
    await spawn_channel(msg)      # 这里才真正 forkpty
```

**注意拒绝发生在 `forkpty` 之前**——不能先起了进程再判断，那样等于给了对方一个 shell。

## 4. `psk_verified` 从哪来

握手时就能确定，不需要额外协议：

| 我的密码 | 对方密码 | 握手结果 | `psk_verified` |
| --- | --- | --- | --- |
| 有 | 有，一致 | 成功 | **true** |
| 有 | 有，不一致 | AEAD 解密失败 | 连接不建立 |
| 有 | 无 | 协商不一致 | 连接建立，但 **false** |
| 无 | 无 | 成功 | **false** |

第三行是关键：**一方有密码一方没有，不应该连不上**——它应该连上，只是没有反向能力。

这比原来的"pwd ↔ no-pwd = 失败"体验好得多：

```
   旧：A(有密码) → B(无密码)   ✗ 连接失败，提示"对方未设密码"
   新：A(有密码) → B(无密码)   ✓ 连上了，A 能控制 B，B 不能反向
                                  B 界面上显示"反向控制需要密码"
```

握手帧里用一个布尔字段协商：

```python
# HELLO
{"from": id_a, "eph": eph_pub_a, "psk_on": True, "sig": ...}

# 会话密钥
ikm = shared + (psk_bytes if both_psk_on else b"")
psk_verified = both_psk_on and decrypt_ok
```

`both_psk_on` 由双方 `psk_on` 取与得到，两端算出同样结果，不需要额外往返。

## 5. `need_psk` 之后怎么办

用户看到"反向控制需要密码"，然后呢？

### v1：重连（简单）

```
   点"输入密码并启用反向控制"
     → 断开 data 连接（session 在宿主侧继续跑，ring buffer 保住输出）
     → 用密码重新握手
     → 重连后 psk_verified = true
     → 再发 OPEN，成功
```

代价：断一次连，当前终端画面要靠 SNAPSHOT 回放恢复。因为 ring buffer 已经设计了，代价很小。

### v2：运行期提权（不重连）

宿主发一个随机 challenge，控制方用 PSK 派生 HMAC 回复：

```
   B → A: {type:"PSK_CHALLENGE", nonce: 32 字节随机}
   A → B: {type:"PSK_RESPONSE", mac: HMAC(psk_mac, nonce || peer_ids)}
   B 校验通过 → psk_verified = True（本次连接内有效）
```

约 30 行。注意：

- 用 `hmac.compare_digest` 比较，防时序攻击
- nonce 一次性，用完即弃，防重放
- MAC 走的是已加密的通道（AES-GCM 里），所以即使被截获也没用

**建议 v1 先做重连版，v2 再优化。** 因为重连逻辑本来就要有（网络断了也得重连），复用它零成本。

## 6. 反向 OPEN 还要人工确认吗

密码验证通过**不等于**可以静默控制。

```
   被动方首次收到反向 OPEN
     → 本机弹窗：「office-mini 请求控制你的终端」
                [ 允许一次 ]  [ 一直允许 ]  [ 拒绝 ]
```

理由：这是**你的机器被别人打开**的场景，风险等级和"你主动连别人"完全不同。即使密码对了，也可能是：
- 对方机器被入侵（私钥被复制，密码在 Keychain 里）
- 对方误操作

所以：**密码是技术门槛，确认是人的门槛。两个都要。**

`一直允许` 写进配置：

```toml
[peer."a3f2c1d8"]
perms        = ["shell", "file"]
psk_required = true
auto_accept  = false        # 反向 OPEN 是否免确认
```

## 7. 三种拒绝原因，界面必须分开

| 原因 | 含义 | 用户能做什么 |
| --- | --- | --- |
| `denied` | 对方 ACL 没授权这类操作 | 让对方加白名单，重试无用 |
| `need_psk` | 缺密码，无法反向 | 输入密码重连 |
| `busy` | 对方已有活跃会话或拒绝 | 稍后重试 |

混在一起会让用户反复点击列表。**`denied` 和 `need_psk` 的区别尤其重要**：前者是对方配置问题，后者是我这边补一个密码就能解决。

---

## 8. 一个容易漏的边界

如果两边都设了同样的密码，那么：

```
   A 点 B  → 连接建立，双方 psk_verified = true
   A 可以控制 B  ✓
   B 可以控制 A  ✓   ← 而且 B 没点过任何东西
```

技术上这是对的（双方都有密码，说明都是同一主人）。但 B 的用户可能觉得"我没点，怎么就被控制了"。

所以第 6 节的确认弹窗在这条路径上**尤其必要**。默认 `auto_accept = false`。

另一个边界：如果 A 和 B 都想控制对方，会各自开一个 shell 通道，互不干扰（channel 方向位不同）。这是设计本意，但 UI 上要让用户看清"我现在在控制谁 / 谁在控制我"：

```
   ┌──────────────────────────────────────────────┐
   │  当前链路  office-mini                        │
   │                                             │
   │  ▸ 我在控制对方    ch 0x0001  shell          │
   │  ▸ 对方在控制我    ch 0x8001  shell  ⚠       │
   │                     [ 断开此通道 ]            │
   └──────────────────────────────────────────────┘
```

第二行必须显眼——这是安全相关的可见性。

---

## 9. 一句话

> **敲门不需要密码，进门之后想反锁主人家的门，得先证明你是主人。**
>
> 建链是敲门。控制对方是进对方的房间。
> 你主动敲门，主人开门让你进，合理；
> 你只是坐在自己家里等，不能因为有人敲过门，就跑去开他家的锁。
