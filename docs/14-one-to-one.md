# 14 · 一对一 · 单向建链 · 双向使用

对模型做最后一次收敛。三句话：

```
   ① 一对一      一次只有一条桥，两个节点
   ② 单向建链    连接由一端主动建立，不互相拨号
   ③ 双向使用    桥一旦通了，两端都能当宿主、都能当控制方
```

这篇取代 `docs/10-symmetric-peer.md` 中"多 bridge / 双向 DIAL / 撞车 tie-break"的部分。

---

## 1. 三个词的精确含义

| 说法 | 指的是 | 不指 |
| --- | --- | --- |
| 一对一 | **拓扑**：一条链路只有两个节点 | 不是"一个会话" |
| 单向建链 | **建立方向**：谁主动连谁 | **不是"数据单向"** |
| 双向使用 | **通道能力**：两端都能发 OPEN | 不是"两个方向同时建立连接" |

最容易错的一处：

> **建链是有向的，通道是对称的。**

```
   建立：  A ────── 主动连 ──────▶ relay ◀────── 被动等 ────── B
                    （有向，只发生一次）

   使用：  A ⇄════════ 桥 ════════⇄ B
           A 可以说"给我一个 shell"  → B spawn
           B 也可以说"给我一个 shell" → A spawn
                    （对称，运行期任意次）
```

把这两件事混在一起，就会做出"两个方向的连接"——那是错的，会引出撞车、双桥、tie-break 这一整串问题。

---

## 2. 一对一删掉了什么

这是本次收敛最大的收益。设计里一整类状态直接消失：

| 之前要处理 | 现在 |
| --- | --- |
| 在线表（N 个节点） | **不需要**，只有一对 |
| 多 bridge 并发管理 | **不需要** |
| 双向同时 DIAL 撞车 | **不需要**，建链单向 |
| `node_id` 字典序 tie-break | **不需要** |
| 单节点 bridge 数上限 | **不需要** |
| bridge 发起方负责重连 | 固定为主动方 |
| 5 种信令帧 | **0 种**（房间模型） |

协议帧从 16 种降到 **10 种**：

```
   保留：HELLO / DATA / OPEN / OPEN_OK / OPEN_ERR / CLOSE
         RESIZE / SNAPSHOT / PING / CLIPBOARD
   删除：REGISTER / DIAL / INCOMING / DIAL_OK / DIAL_ERR
```

## 3. 架构

```
   ┌──────────────────────────────────────────────────────────────┐
   │  云主机 · relay（房间门房）                                      │
   │     rooms: "room_key" → [wsA, wsB]                            │
   │     房间里满两个就把两头接上，其余一概不管                          │
   └───────────▲──────────────────────────────▲──────────────────┘
               │                              │
        wss /r/<room>                  wss /r/<room>
               │                              │
   ┌───────────┴──────────┐      ┌────────────┴──────────┐
   │  home-mbp            │      │  office-mini          │
   │  active = true       │      │  active = false       │
   │  （主动建立）           │      │  （只等对方来）          │
   │                      │      │                       │
   │  ┌────────────────┐  │      │  ┌─────────────────┐  │
   │  │ Broker         │  │      │  │ Broker          │  │
   │  │ 我是宿主的会话    │  │      │  │ 我是宿主的会话     │  │
   │  ├────────────────┤  │      │  ├─────────────────┤  │
   │  │ Remote         │  │      │  │ Remote          │  │
   │  │ 我是控制方的会话  │  │      │  │ 我是控制方的会话   │  │
   │  └────────────────┘  │      │  └─────────────────┘  │
   └──────────────────────┘      └───────────────────────┘
```

两边**程序完全一样**，差别只在配置里一个 `active` 布尔值。

---

## 4. 配置

```toml
# ~/.rpty/config.toml  —— 家机
[node]
name = "home-mbp"

[link]
peer   = "a3f2c1d8"                    # office-mini 的 node_id
relay  = "wss://relay.example.com"
active = true                          # 本机主动建立链路
retry  = [5, 10, 30, 60]               # 退避序列（秒）

[acl."a3f2c1d8"]
name  = "office-mini"
perms = ["shell", "file"]
```

```toml
# ~/.rpty/config.toml  —— 公司机
[node]
name = "office-mini"

[link]
peer   = "5e9b0a71"                    # home-mbp 的 node_id
relay  = "wss://relay.example.com"
active = false                         # 只等对方来，不主动外连

[acl."5e9b0a71"]
name  = "home-mbp"
perms = ["shell"]                      # 只允许它开 shell，不许读文件
```

`active` 是**每条链路**的属性，不是机器的角色。一台机器如果有多条链路，可以一条 active、一条 passive。

---

## 5. 连接生命周期

```
   home-mbp (active)                     relay                     office-mini (passive)
        │                                  │                              │
        │  ── wss /r/<room> ──────────────▶│                              │
        │                                  │◀──────── wss /r/<room> ──────│
        │                                  │                              │
        │                                  │  房间里有 2 个 → 桥接          │
        │  ◀══════════════ 纯字节管道 ══════════════════════════════════▶  │
        │                                  │                              │
        │  ── HELLO + 签名 ───────────────────────────────────────────▶  │
        │  ◀─ HELLO + 签名 ───────────────────────────────────────────    │
        │     双方互换 node_id，各自查 ACL，不在白名单就断开                  │
        │                                  │                              │
        │  ── OPEN{ch:0x0001, kind:shell} ────────────────────────────▶  │
        │  ◀─ OPEN_OK{ch:0x0001} ─────────────────────────────────────    │
        │                                  │   office-mini spawn PTY      │
        │  ◀═════ DATA（终端字节）═══════════════════════════════════    │
        │                                  │                              │
        │  ◀─ OPEN{ch:0x8001, kind:file} ─────────────────────────────    │  ← 反向也能开
        │  ── OPEN_OK{ch:0x8001} ────────────────────────────────────▶   │
```

注意最后两行：**同一条桥上，两个方向各开一个通道，互不干扰。**

---

## 6. 谁发起？三种策略

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 固定一端 active**（推荐） | 配置里指定 | 最简单，无歧义 | 主动方离线时整条链路不可用 |
| B. 两端都 active | 双方都连同一房间 | 任一端在线即可用 | 需要房间模型天然去重（见下） |
| C. 轮流 | 定时切换 | 均衡 | 复杂，无收益 |

**推荐 A**，因为它最符合"单向建链"的语义，也没有任何协调逻辑。

但如果想要"任一端在线都能用"，B 其实也是安全的——**这是房间模型相比 DIAL 模型的一个额外好处**：

```
   房间模型：两端连同一个 room_key，谁先到谁等，第二个到了就桥
             → 天然只有一条桥，不会出现"双桥"
   DIAL 模型：两条独立的 DIAL 请求可能交叉
             → 需要 tie-break
```

所以房间模型下"两端都 active"不需要撞车处理，relay 那 90 行代码一行都不用改。

结论：**A 和 B 在实现上没有成本差异，只是配置不同的两个值。** 默认 A，需要时改 B。

---

## 7. 一对一的限制

| 限制 | 影响 | 应对 |
| --- | --- | --- |
| 同时只有一条活跃链路 | 不能一边连公司一边连家里 NAS | 需要时 `rpty switch <peer>` 切换（断开再连） |
| 主动方离线 → 整条链路不可用 | 家机没开就没法用 | 用策略 B（两端都 active） |
| 通道数量受单连接带宽限制 | 传大文件时终端会卡 | 通道级流控（已规划） |

如果以后确实需要"同时连两台"，那就回到 `docs/10` 的多 bridge 模型——**协议层不用改，只是 relay 允许一个节点出现在多个房间里。** 这是加分项，不是返工。

## 8. 代码量

| 组件 | 之前（多 bridge + DIAL） | 现在（一对一 + 房间） |
| --- | --- | --- |
| relay | 250 行 | **90 行** |
| peer 建连逻辑 | ~200 行 | **~80 行** |
| 协议帧 | 16 种 | **10 种** |
| 需处理的状态边界 | 撞车 / 顶替 / 多桥 / 超时 | **房间满 / 对端断开** |

整体首版可以压到 **500 行左右**（不含加密与 UI）。

## 9. 一句话

> **一条桥，两个人。一个人先敲门，门开了两个人都能递东西。**
> 谁敲门是配置决定的，递什么、递给谁，是每开一个通道时决定的。
