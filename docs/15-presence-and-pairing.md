# 15 · 在线列表与点击配对（历史）

> 2026-11-28：本文的「点一下 = 自动配对」**已下线**。单向把别人拉进会话正是要防的事，
> 现在是「点卡片 + 输对方的通话密码 = 直接建一对一房间」（2026-11-28 起，不再有同意环节）。
> 在线列表还在，配对表没了。
> 现行语义见 `docs/12-concept-model.md` 与 `docs/34-client-identity.md`。

交互层的最终形态：

```
   打开客户端 → 看到在线列表 → 点一下 → 自动配对 → 开始用
```

这篇补充 `docs/14-one-to-one.md`：一对一、双向使用不变，但**建链方式从"配置 active"升级为"点击决定"**。

---

## 1. 这个交互带来什么变化

| 项 | 14 的模型（房间） | 本模型（presence） |
| --- | --- | --- |
| relay 状态 | 房间字典 | **在线表 + 配对表** |
| 能否感知在线 | ✗ | ✓ |
| 谁发起 | 配置 `active` | **点击的那一方** |
| 代码量 | 90 行 | **约 170 行** |
| 协议帧 | 10 种 | 10 + 6 种信令 |

代价：relay 多 80 行，多一层生命周期管理（心跳、超时清理）。

收益：**`active` / `passive` 配置彻底消失**。谁点谁发起，方向由用户操作决定，天然单向，不需要任何约定。这是真实简化。

---

## 2. 关键设计：两条连接，职责分离

如果只用一条连接，配对后它变成纯字节管道，就再也不能收信令了——列表会消失，也没法切换对端。

所以拆成两条：

```
   ┌──────────────────────────────────────────────────────────────┐
   │  control 连接  ·  常驻  ·  JSON  ·  轻量                       │
   │    职责：注册、拉列表、订阅上线通知、发起 DIAL                    │
   │    URL：wss://relay/ctl                                        │
   │    特征：几十字节/分钟，几乎不占带宽                               │
   ├──────────────────────────────────────────────────────────────┤
   │  data 连接     ·  按需  ·  二进制帧  ·  重                         │
   │    职责：承载通道（shell / file / forward）                      │
   │    URL：wss://relay/d/<pair_id>                                │
   │    特征：配对成功后由 relay 桥接，进入纯字节搬运                     │
   └──────────────────────────────────────────────────────────────┘
```

好处：

- 列表永远在，随时能看到谁上线了
- 断开数据连接不影响在场状态
- 切换对端只需关掉旧 data、开新 data，control 不动
- relay 的两类连接逻辑互不干扰，代码更容易写对

代价：relay 要区分两类连接（看 URL path 即可，成本几乎为零）。

## 3. 完整时序

```
   客户端A              relay              客户端B
   (home-mbp)                          (office-mini)
      │                  │                  │
      ├── REGISTER ─────▶│                  │
      │  {node_id,name}  │                  │
      │◀── REG_OK ───────┤                  │
      │                  │◀── REGISTER ─────┤
      │                  ├── PUSH(上线) ───▶│
      │◀─ PUSH(上线) ────┤                  │
      │                  │                  │
      │  ▸ UI: ● office-mini 在线            │
      │  ▸ 用户点击                          │
      │                  │                  │
      ├── DIAL ─────────▶│                  │
      │  {target}        ├── INCOMING ────▶│
      │                  │                  │  查 ACL → 通过
      │                  │◀── ACK ──────────┤
      │◀─ DIAL_OK ───────┤                  │
      │  {pair_id}       ├── DIAL_OK ──────▶│
      │                  │  {pair_id}       │
      │                  │                  │
      ├── wss /d/pair ──▶│◀── wss /d/pair ──┤   ← 各自新开一条 data 连接
      │                  │  两条到齐 → 桥接   │
      │◀═══════════════════════════════════▶│
      │                  │                  │
      │  ── HELLO（E2E 握手，relay 看不懂）──▶│
      │  ◀─────────────────────────────────  │
      │                  │                  │
      │  ── OPEN{ch:1, kind:shell} ────────▶│
      │  ◀─ OPEN_OK{ch:1} ─────────────────  │
      │                  │   B spawn PTY     │
      │  ◀══════ DATA（终端字节）════════════  │
```

要点：

- `pair_id` 是 relay 生成的一次性随机串，只在这次配对有效，防止别人猜 URL 插进来
- 两条 data 连接都到位后，relay 立即桥接并扔掉 `pair_id`
- 之后 relay 对这条链路完全透明

## 4. 列表显示谁：不做全局广播

这是最容易做错的隐私点。

### 错误做法

```
   relay 广播：所有在线节点列表 → 发给所有连接
   后果：任何能连 relay 的人都知道你有几台机器、叫什么名字
```

### 正确做法

```
   客户端启动时，从本地配置读出"我关心的人"（就是 ACL 里的 peer 列表）
       ↓
   向 relay 提交：LIST { peers: ["a3f2c1d8", "5e9b0a71"] }
       ↓
   relay 只回这几个的在线状态
```

```json
→ { "type": "LIST", "peers": ["a3f2c1d8", "5e9b0a71"] }
← { "type": "ONLINE", "map": { "a3f2c1d8": true, "5e9b0a71": false } }
```

好处：

- relay 不主动广播任何人的存在
- 陌生人连上 relay，看到的是空列表（它不知道该查谁）
- 列表内容 = 你的 ACL，本地持有，relay 只知道"有人在查这几个 ID"

进一步：如果不想让 relay 知道关系图，可以让客户端对 `node_id` 做本地哈希后再查，relay 只比对哈希。这属于可选加固，v2 再说。

## 5. UI 上要表达四件事

列表不是"在线/离线"两个状态就够的：

```
   ┌──────────────────────────────────────────┐
   │  ● office-mini          在线 · 可连接      │
   │  ○ home-nas             离线              │
   │  ◐ office-mini          在线 · 已连接      │  ← 当前活跃链路
   │  ⊘ old-mbp              在线 · 未授权      │  ← 对方 ACL 没放我
   └──────────────────────────────────────────┘
```

| 状态 | 含义 | 点击行为 |
| --- | --- | --- |
| ● 在线 | 对方在 relay 上 | 发起 DIAL |
| ○ 离线 | 对方没连 | 置灰，提示"对方未上线" |
| ◐ 已连接 | 当前活跃链路 | 点击 = 查看会话列表 |
| ⊘ 未授权 | 对方拒绝了我 | 提示"对方未把你加入白名单"，不重试 |

最后一种很重要：**"对方未授权"和"连接失败"必须区分**。前者是配置问题，重试一百次也没用；后者是网络问题，可以重试。混在一起会让用户反复点击。

---

## 6. 一对一意味着"点另一个就先断开"

因为是一对一，点击一个新的对端时：

```
   当前链路 office-mini
       ↓ 用户点击 home-nas
   ① 提示"将断开与 office-mini 的连接"
   ② 关闭 data 连接（session 在宿主侧继续跑，ring buffer 保住输出）
   ③ 对 home-nas 发起 DIAL
   ④ 新 data 连接建立
   ⑤ 列表显示 ◐ home-nas
```

关键：**断开的是 data 连接，不是 session。** 宿主那边的 shell 还在跑，下次连回来能看到之前的输出。这是 `docs/10` 里 ring buffer 设计的直接收益。

## 7. 代码量

| 组件 | 行数 |
| --- | --- |
| relay：在线表 + LIST + DIAL + 信令转发 | ~110 |
| relay：data 连接配对与桥接 | ~60 |
| **relay 合计** | **~170** |
| peer：control 连接与列表状态 | ~120 |
| peer：建连流程（DIAL → 等 pair_id → 开 data） | ~90 |
| peer：通道层（不变） | — |

相对 14 的 90 行多了 80 行，但换来的是"点一下就连"这个体验差异。**这个交换值得。**

## 8. 帧表（最终）

### control 连接（JSON）

| type | 方向 | 说明 |
| --- | --- | --- |
| `REGISTER` | C→S | `{node_id, name, version}` |
| `REG_OK` | S→C | `{peers_online}` |
| `LIST` | C→S | `{peers: [...]}` 我只关心这些 |
| `ONLINE` | S→C | `{map: {node_id: bool}}` |
| `PUSH` | S→C | `{node_id, online}` 状态变化推送 |
| `DIAL` | C→S | `{target}` |
| `INCOMING` | S→C | `{from, name}` |
| `ACK` | C→S | `{from}` 被叫方同意 |
| `REJ` | C→S | `{from, reason}` 拒（ACL / 忙碌） |
| `DIAL_OK` | S→C | `{pair_id, url}` |
| `DIAL_ERR` | S→C | `{reason}` offline / denied / timeout |
| `PING` / `PONG` | 双向 | |

### data 连接（二进制帧）

| type | 说明 |
| --- | --- |
| `HELLO` | E2E 握手（X25519 + 签名） |
| `DATA` | 通道数据（密文） |
| `OPEN` / `OPEN_OK` / `OPEN_ERR` | 通道建立 |
| `CLOSE` | 关通道 |
| `RESIZE` | 终端尺寸 |
| `SNAPSHOT` | 重连画面回放 |
| `PING` | 心跳 |

---

## 9. 一句话

> **control 是名片和通讯录，data 是电话线。**
> 名片一直在，电话线打完就挂。挂断不影响对方家里该干的事。
